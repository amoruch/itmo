# Лабораторная работа № 6 — клиент-серверное приложение

Продолжение [лабораторной работы № 5](../programming_lab5). Программа управляет коллекцией объектов `SpaceMarine`. В этой версии логика работы с коллекцией перенесена на сервер, а клиент отвечает за ввод команд, валидацию данных и вывод результатов.

## Требования задания

- Обработку объектов коллекции необходимо выполнять с помощью Stream API и лямбда-выражений.
- Между клиентом и сервером передаются сериализованные объекты, а не строки команд.
- Коллекция, отправляемая клиенту, сортируется в естественном порядке объектов `SpaceMarine`.
- Клиент корректно сообщает о временной недоступности сервера.
- Обмен выполняется по протоколу UDP с использованием неблокирующих сетевых каналов.
- Обработка UDP-запросов работает в отдельном потоке, а консоль сервера остаётся доступна в главном потоке.
- Сервер хранит коллекцию в JSON-файле, назначает `id` и `creationDate` новым объектам и сохраняет данные при штатном завершении.
- Команда `save` доступна только в консоли сервера. Команда `exit` клиента завершает только клиент.

Дополнительное задание из ТЗ — журналирование этапов работы сервера через Log4J2. В текущем проекте оно **не реализовано**: сервер выводит служебные сообщения в консоль и не содержит зависимости Log4J2.

## Структура проекта

Проект собирается Maven и состоит из трёх модулей:

```text
programming_lab6/
├── common/       # модель SpaceMarine и объекты сетевого протокола
├── client/       # консольный клиент
├── server/       # UDP-сервер, команды, JSON-хранилище
├── report_latex/ # исходники отчёта и UML-диаграмма
├── collection.json
└── pom.xml       # родительский Maven-проект
```

### Общий модуль `common`

- `Model` содержит `SpaceMarine`, `Coordinates`, `Chapter` и перечисления полей.
- `Protocol` определяет перечисление `CommandType`, классы `Request` и `Response`, типизированные аргументы команд (`Empty`, `Id`, `Marine`, `Update`) и методы сериализации.
- `DatagramTransfer` задаёт общий формат фрагментации UDP-сообщений, а `ZonedDateTimeAdapter` — JSON-представление даты модели.

### Сервер

| Ответственность | Реализация |
| --- | --- |
| Запуск приложения и консоль сервера | `server.Main` |
| Приём, обработка и отправка UDP-датаграмм | `DatagramServer`, `DatagramTransfer` |
| Регистрация и история команд | `managers.CommandManager` |
| Выбор и выполнение команд | `managers.ServerCommandManager`, пакет `server.commands` |
| Операции с коллекцией | `managers.CollectionManager` |
| Загрузка и сохранение JSON | `managers.DumpManager`, `common.ZonedDateTimeAdapter` |

`Main` создаёт менеджеры по схеме ЛР5: `DumpManager`, `CollectionManager`, `CommandManager`. Затем он запускает `DatagramServer` в отдельном потоке и передаёт консольный цикл `ServerCommandManager`. `CommandManager` хранит таблицу команд и историю последних 12 сетевых запросов; `save` и `exit` доступны только в консоли сервера. Каждая операция коллекции находится в отдельном классе с коротким именем: `Add`, `Show`, `Save`, `Exit` и т.д.

### Клиент

- `Main` создаёт `CommandManager` и консоль, затем запускает последовательный цикл ввода.
- `managers.CommandManager` хранит таблицу команд, выполняет интерактивный цикл и запускает скрипты с защитой от рекурсии.
- `utility.Ask` считывает и проверяет поля `SpaceMarine`.
- `utility.Console` и `utility.StandardConsole` отделяют вводимые данные от их отображения в консоли.
- `DatagramClient` сериализует запрос, отправляет его по UDP и синхронно ожидает ответ не более 2,5 секунд без использования `Selector`.
- Классы в `client.commands` имеют короткие имена (`Add`, `Show`, `Exit` и т.д.), создают типизированные запросы и не содержат сетевой логики. Локальными остаются `help`, `exit` и `execute_script`; сохранение коллекции выполняется на сервере.

### Передача больших сообщений

Класс `DatagramTransfer` используется и клиентом, и сервером. Сериализованный объект разбивается на части по 8192 байта данных. Последний байт каждой UDP-датаграммы — флаг: `1` означает, что далее следует ещё одна часть, `0` — что сообщение завершено. Получатель соединяет части до появления флага `0`, затем десериализует исходный объект.

При потере части UDP-сообщения данные не будут десериализованы, а клиент получит тайм-аут и сможет повторить команду. Это сознательно простая схема для лабораторной работы; UDP не гарантирует доставку и порядок пакетов.

## Сборка

Нужны JDK 17+ и Maven 3.9+.

```bash
mvn clean package
```

Maven сам загружает Gson. Папка `libs` не нужна. После успешной сборки создаются исполняемые JAR-файлы:

```text
client/target/client.jar
server/target/server.jar
```

## Запуск

Откройте два терминала из корня проекта. Сначала запустите сервер, передав ему свободный UDP-порт и файл коллекции:

```bash
java -jar server/target/server.jar 8000 collection.json
```

Затем запустите клиент:

```bash
java -jar client/target/client.jar 127.0.0.1 8000
```

Если аргументы не переданы, обе программы используют порт `5050`, а сервер — файл `collection.json` в текущей директории. Порт должен быть свободен.

## Команды клиента

| Команда | Назначение |
| --- | --- |
| `help` | вывести справку по доступным командам |
| `info` | вывести сведения о коллекции |
| `show` | вывести элементы коллекции в естественном порядке |
| `add` | добавить новый элемент; поля запрашиваются по очереди |
| `update id` | обновить элемент с указанным `id` |
| `remove_by_id id` | удалить элемент по идентификатору |
| `clear` | очистить коллекцию |
| `remove_first` | удалить первый элемент коллекции |
| `add_if_max` | добавить элемент, если он больше текущего максимального |
| `remove_lower` | удалить элементы, меньшие введённого |
| `max_by_health` | вывести элемент с максимальным `health` |
| `group_counting_by_creation_date` | сгруппировать элементы по дате создания |
| `print_descending` | вывести элементы в порядке убывания |
| `history` | вывести последние выполненные команды |
| `execute_script file_name` | выполнить команды из текстового файла на клиенте |
| `exit` | завершить клиентское приложение |

Поля объекта после команд `add`, `update`, `add_if_max` и `remove_lower` вводятся в интерактивном режиме. При вводе из файла параметры указываются на последующих строках в том порядке, в котором их запрашивает клиент.

Команды `save` в клиенте нет: при её вводе клиент напомнит, что сохранение доступно только серверу.

## Команды сервера

Сервер одновременно принимает сетевые запросы и обрабатывает две команды из собственной консоли:

| Команда | Назначение |
| --- | --- |
| `save` | немедленно сохранить текущую коллекцию в JSON-файл |
| `exit` | завершить сервер; перед завершением коллекция сохраняется автоматически |

Все команды управления коллекцией выполняются только после запроса клиента. Это не дублирование интерфейса клиента: сервер владеет данными и исполняет полученные типизированные запросы.

## Проверка работы

Минимальный сценарий ручной проверки:

1. Собрать проект и запустить сервер на порту `8000`.
2. Подключить клиент и выполнить `help`, `info`, `show`.
3. Добавить объект командой `add`, затем проверить его через `show`.
4. Выполнить `history`, `max_by_health` или `print_descending`.
5. В консоли сервера выполнить `save`, затем `exit`.
6. Запустить сервер повторно с тем же `collection.json` и убедиться, что добавленный объект загрузился.
7. Запустить клиент с неверным портом и убедиться, что выводится сообщение о временной недоступности сервера.

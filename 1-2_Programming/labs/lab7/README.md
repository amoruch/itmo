# Лабораторная работа № 7 — многопользовательское клиент-серверное приложение

Продолжение лабораторной работы № 6. Программа управляет коллекцией объектов `SpaceMarine`: клиент считывает команды и выводит результат, а сервер выполняет операции, хранит данные в PostgreSQL и обменивается с клиентом UDP-датаграммами.

## Требования задания

- Коллекция и учётные записи пользователей хранятся в PostgreSQL.
- Перед работой с коллекцией необходимо зарегистрироваться или авторизоваться.
- Все авторизованные пользователи видят коллекцию, но изменяют и удаляют только собственные объекты.
- Пароли хранятся как SHA-224-хэши.
- Сервер использует JDBC, потокобезопасные структуры данных и Log4j2.
- Отдельный поток принимает UDP-запросы, для обработки каждого запроса создаётся новый поток, а ответы отправляются кэшируемым пулом потоков.

## Структура проекта

```text
lab7/
├── common/       # модель SpaceMarine и сериализуемый сетевой протокол
├── client/       # консольный UDP-клиент
├── server/       # команды, JDBC-репозитории, UDP-сервер и Log4j2
├── sql/          # схема PostgreSQL, начальное заполнение и проверки
├── report_latex/ # LaTeX-исходники отчёта и UML-диаграммы
└── pom.xml       # родительский Maven-проект
```

### Общий модуль `common`

`Model` содержит `SpaceMarine`, `Coordinates`, `Chapter` и перечисления. В `Protocol` находятся сериализуемые `Request` и `Response`, аргументы команд и `Credentials`. После успешной команды `register` или `login` клиент прикладывает учётные данные к каждому запросу. `DatagramTransfer` фрагментирует большие сообщения: последним байтом датаграммы передаётся флаг продолжения (`1`) либо окончания (`0`).

### Сервер

| Ответственность | Реализация |
| --- | --- |
| Подключение к PostgreSQL | `managers.DatabaseManager` |
| Пользователи и SHA-224 | `utility.UserRepository` |
| Объекты и SQL-операции | `utility.MarineRepository` |
| Коллекция в памяти | `managers.CollectionManager` |
| Авторизация и выполнение запроса | `managers.RequestHandler` |
| Приём, обработка и отправка UDP | `managers.DatagramServer` |

При старте `CollectionManager` загружает объекты из базы в `ConcurrentHashMap` и `ConcurrentSkipListSet`. Читающие команды используют память; изменяющие команды удерживают блокировку, сначала выполняют параметризованный SQL-запрос и только затем обновляют память. PostgreSQL назначает `id` и `creation_date` новых объектов через `IDENTITY`, `DEFAULT` и `RETURNING`.

В SQL-запросах изменения ограничены условием `creator_id = ?`, поэтому пользователь не может изменить чужой объект. Журнал работы сервера выводится в консоль и в файл `logs/server-<дата-время>.log`.

### Клиент

`Main` создаёт `ClientRunner`, консоль и `DatagramClient`. `ClientRunner` хранит учётные данные только в памяти текущего процесса, выполняет команды и отображает ответ. Команды в `client.commands` формируют типизированные запросы; локальными остаются `help`, `execute_script` и `exit`.

## Подготовка базы данных

Скрипты рассчитаны на PostgreSQL и схему `public` базы `lab7`. Подробная инструкция находится в [sql/README.md](sql/README.md). Из корня `lab7` в PowerShell:

```powershell
$psql = 'C:\Program Files\PostgreSQL\17\bin\psql.exe'
& $psql -U postgres -d lab7 -f sql/01_create_schema.sql
& $psql -U postgres -d lab7 -f sql/02_seed_collection.sql
& $psql -U postgres -d lab7 -f sql/04_replace_enum_checks.sql
& $psql -U postgres -d lab7 -f sql/03_verify_data.sql
```

Начальное заполнение переносит семь объектов из прежней коллекции. Оно также создаёт пользователей `initial_import` / `initial-import`, `captain` / `captain-pass`, `scout` / `scout-pass` и `medic` / `medic-pass` для проверки доступа.

## Настройка подключения

Настройки читаются сначала из системных свойств Java, затем из переменных окружения.

| Переменная | Значение по умолчанию |
| --- | --- |
| `LAB7_DB_URL` | `jdbc:postgresql://localhost:5432/lab7` |
| `LAB7_DB_USER` | `postgres` |
| `LAB7_DB_PASSWORD` | пустая строка |

Пример для PowerShell:

```powershell
$env:LAB7_DB_PASSWORD = 'ваш_пароль_от_PostgreSQL'
```

## Сборка и запуск

Нужны JDK 17+ и Maven 3.9+. Из корня проекта:

```powershell
mvn clean package
```

После сборки создаются `client/target/client.jar` и `server/target/server.jar`.

Сначала запустите сервер; первый аргумент — UDP-порт, по умолчанию `8000`:

```powershell
java -jar server/target/server.jar 8000
```

Затем в другом терминале запустите клиента. Аргументы — адрес и порт; по умолчанию используются `127.0.0.1` и `8000`:

```powershell
java -jar client/target/client.jar 127.0.0.1 8000
```

На сервере доступна только локальная команда `exit`. Сохранять коллекцию перед остановкой не требуется: каждая изменяющая операция уже записана в БД.

## Команды клиента

| Команда | Назначение |
| --- | --- |
| `register login password` | зарегистрироваться и авторизоваться |
| `login login password` | войти под существующей учётной записью |
| `help` | вывести справку |
| `info` | вывести сведения о коллекции |
| `show` | вывести все объекты в естественном порядке |
| `add` | добавить объект от имени текущего пользователя |
| `update id` | изменить собственный объект с указанным `id` |
| `remove_by_id id` | удалить собственный объект |
| `clear` | удалить все собственные объекты |
| `remove_first` | удалить первый собственный объект |
| `add_if_max` | добавить объект, если он больше максимального |
| `remove_lower` | удалить собственные объекты, меньшие введённого |
| `max_by_health` | вывести объект с максимальным `health` |
| `group_counting_by_creation_date` | сгруппировать объекты по дате создания |
| `print_descending` | вывести объекты по убыванию |
| `history` | показать историю серверных команд |
| `execute_script file_name` | выполнить команды из файла |
| `exit` | завершить клиент |

## Проверка работы

1. Подготовьте БД, соберите проект и запустите сервер.
2. Войдите командой `login captain captain-pass`, выполните `show` и `info`.
3. Добавьте объект и убедитесь через `show`, что сервер назначил ему `id` и дату создания.
4. Во втором клиенте войдите как `scout` и попробуйте изменить либо удалить объект `captain`: сервер должен отказать.
5. Повторите операцию под `captain`, затем перезапустите сервер и убедитесь, что изменение сохранилось.
6. Проверьте файл журнала в каталоге `logs`.

## 0. Введение

Веб-программирование — это разработка приложений, работающих в условиях Всемирной паутины. Несмотря на огромное разнообразие фреймворков и подходов (от простых HTML-страниц до сложных SPA и микросервисов), «под капотом» у всех лежат одни и те же базовые стандарты и протоколы. Этот раздел — о них.

### Архитектура клиент-сервер

**Клиент-серверная архитектура** — это модель взаимодействия, в которой одна сторона (**клиент**) запрашивает ресурсы или услуги, а другая (**сервер**) их предоставляет. В вебе клиентом обычно выступает **браузер**, а сервером — **веб-сервер** (например, `httpd`, `nginx`, `Apache`).

Обмен данными идёт по схеме **«запрос-ответ»** (`request-response`):

1. Клиент устанавливает соединение с сервером.
2. Клиент отправляет **HTTP-запрос** (что он хочет получить или сделать).
3. Сервер обрабатывает запрос и возвращает **HTTP-ответ** (результат или ошибку).

Простейшая иллюстрация (структура запроса и ответа будет подробно разобрана в следующем разделе):

```http
GET /index.html HTTP/1.1
Host: example.com
```

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8

<!DOCTYPE html>
<html>...</html>
```

**Ключевое понятие — ресурс.** Клиент запрашивает не «файл на диске», а **ресурс**, идентифицируемый с помощью URI. Ресурсом может быть HTML-страница, изображение, JSON-документ, результат вычисления («текущая погода в Москве») — что угодно, что можно идентифицировать и передать. Сервер отдаёт **представление** (representation) этого ресурса в одном из форматов (HTML, JSON, XML, PNG). Один ресурс может иметь несколько представлений, и клиент через заголовки (например, `Accept`) сообщает, какое предпочитает.

**HTTP — stateless-протокол.** Это значит, что каждый запрос **семантически независим**: сервер не обязан помнить, что было в предыдущем запросе, чтобы понять текущий. Соединение может быть разорвано после ответа, а следующий запрос может уйти на другой сервер (если работает балансировщик) — и это нормально. Stateless-дизайн даёт **масштабируемость**: серверы не хранят состояние клиентов, поэтому их можно легко добавлять и убирать, а запросы — распределять по разным машинам. Плата за это — необходимость передавать всю необходимую информацию (например, токен авторизации) в **каждом** запросе.

Здесь часто возникает вопрос: если HTTP не хранит состояние, как тогда работают корзины в интернет-магазинах и сессии пользователей? Ответ в том, что состояние выносится на клиент (cookies, localStorage) или на сервер (сессии в базе данных, Redis), а сам HTTP остаётся лишь «транспортом». Сервер получает идентификатор сессии в каждом запросе (например, через заголовок `Cookie`) и по нему восстанавливает контекст.

Если хотите углубиться в теорию, рекомендую прочитать официальную спецификацию [RFC 9110: HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html) (разделы 3.3 и 3.4 про клиент-сервер и stateless) или статью [MDN: Client-Server overview](https://developer.mozilla.org/en-US/docs/Learn/Server-side/First_steps/Client-Server_overview).

### URI, URL и URN

Эти три аббревиатуры часто путают, но различие между ними принципиально.

- **URI** (Uniform Resource Identifier) — **унифицированный идентификатор ресурса**. Это общее понятие: любая строка, которая однозначно идентифицирует какой-либо ресурс (абстрактный или физический).
- **URL** (Uniform Resource Locator) — **унифицированный локатор ресурса**. Это URI, который говорит **где** ресурс находится и **как** к нему получить доступ (по какому протоколу, на каком хосте, по какому пути).
- **URN** (Uniform Resource Name) — **унифицированное имя ресурса**. Это URI, который даёт ресурсу **уникальное и постоянное имя**, не зависящее от его текущего местоположения. URN остаётся неизменным, даже если ресурс переехал или перестал существовать.

**Отношения между ними:** URL и URN — это **подмножества** URI. Любой URL является URI, но не любой URI является URL.

**Примеры:**

| Тип                      | Пример                           | Комментарий                                                                                              |
| ------------------------ | -------------------------------- | -------------------------------------------------------------------------------------------------------- |
| URL                      | `https://example.com/index.html` | Говорит: «Возьми файл `index.html` с хоста `example.com` по протоколу HTTPS».                            |
| URN                      | `urn:isbn:978-5-17-022457-0`     | Говорит: «Это книга с таким-то ISBN». Не говорит, где её взять.                                          |
| URI (но не URL и не URN) | `mailto:user@example.com`        | Идентифицирует почтовый адрес, но не является ни «локатором» в сетевом смысле, ни «именем» в смысле URN. |

На практике в вебе мы почти всегда имеем дело с **URL**. Термин «URI» чаще встречается в стандартах и документации.

Может ли URL быть одновременно и URN? В строгом смысле — нет, это разные способы идентификации. Однако существуют схемы вроде `urn:`, которые используются внутри URL (например, `https://example.com/resolve?urn=...`), но сам URL при этом остаётся локатором. Для быстрого повторения форматов можно заглянуть в [MDN: What is a URL?](https://developer.mozilla.org/en-US/docs/Learn/Common_questions/Web_mechanics/What_is_a_URL), а на Linux-системах краткое и точное описание всегда доступно по команде `man 7 uri`.

### Браузер

**Браузер** — это программа, которая отображает HTML-документ в его отформатированном виде. Однако современный браузер — это не просто «читалка» тегов, а огромная экосистема, которая умеет работать с JS, CSS, изображениями, сетевыми запросами (HTTP), локальным хранилищем (Cookies, LocalStorage) и видеокодеками. Внутри браузера можно выделить несколько ключевых компонентов:
*   **Движок рендеринга** (Rendering Engine): отвечает за парсинг HTML и CSS, построение DOM-дерева и отрисовку страницы на экране. Примеры: Blink (Chrome, Edge, Opera), WebKit (Safari), Gecko (Firefox).
*   **Движок JavaScript** (JS Engine): выполняет код. Примеры: V8 (Chrome, Node.js), SpiderMonkey (Firefox), JavaScriptCore (Safari).
*   **Сетевой стек**: реализует протокол HTTP/HTTPS, управляет cookies и кешем.

Часто возникает путаница между браузером и поисковиком. Это разные вещи. **Поисковик** (Google, Яндекс) — это сервис, который ищет и индексирует страницы по запросу пользователя и возвращает ссылки на них. **Браузер** (Chrome, Firefox) — это программа, которая эти страницы загружает и отображает. Они часто тесно интегрированы (например, в адресной строке Chrome можно вводить поисковые запросы), но концептуально это разные сущности.

Ещё один важный аспект — **кросс-браузерность**. Разные браузеры используют разные движки рендеринга и имеют разные *user agent stylesheet* (стили по умолчанию для тегов). Именно из-за этого один и тот же HTML-код может выглядеть в Firefox и Safari немного по-разному. Раньше (в эпоху IE6) это создавало огромные проблемы для верстальщиков, сейчас ситуация гораздо лучше благодаря стандартам W3C и WHATWG, но полностью проблема не исчезла.

Если хотите узнать, как браузер отрисовывает страницу шаг за шагом (от байтов до пикселей), в сети есть отличная статья [«Как браузеры работают»](https://web.dev/howbrowserswork/) от разработчиков Google.

### REST (Representational State Transfer)

**REST** — это **архитектурный стиль** для построения распределённых систем, впервые описанный **Роем Филдингом** (одним из авторов HTTP) в его докторской диссертации в 2000 году. REST не является протоколом или стандартом; это набор ограничений, которые, если их соблюдать, дают системе определённые свойства (масштабируемость, простоту, эволюционируемость).

**Основные принципы REST:**

1. **Клиент-сервер** — разделение ответственности: клиент занимается пользовательским интерфейсом, сервер — хранением и обработкой данных.
2. **Stateless** — каждый запрос содержит всю информацию, необходимую для его понимания. Сервер не хранит состояние клиента между запросами.
3. **Кеширование** — ответы сервера могут быть помечены как кешируемые, чтобы клиент мог их переиспользовать.
4. **Единообразный интерфейс** (uniform interface) — ключевой принцип. Он включает идентификацию ресурсов через URI, манипуляцию ресурсами через **представления** (например, JSON), самоописываемые сообщения (заголовки, коды ответов) и **HATEOAS** (Hypermedia as the Engine of Application State) — ответы содержат ссылки на связанные действия (на практике соблюдается редко).
5. **Слои** (layered system) — клиент не знает, общается он с конечным сервером или с промежуточным прокси/балансировщиком.
6. **Код по требованию** (code on demand, опционально) — сервер может передавать клиенту исполняемый код (например, JavaScript).

**REST vs RPC.** Главное отличие: REST моделирует **ресурсы** (сущности), а RPC (Remote Procedure Call) — **операции** (действия). В REST мы говорим: «дай мне ресурс `/users/42`» или «создай новый ресурс в коллекции `/users`». В RPC мы вызываем удалённую процедуру: `getUser(42)` или `createUser(...)`.

**Пример RESTful API:**

| Действие                        | HTTP-метод | URI         | Что делает                                   |
| ------------------------------- | ---------- | ----------- | -------------------------------------------- |
| Получить список пользователей   | `GET`      | `/users`    | Возвращает массив пользователей.             |
| Получить одного пользователя    | `GET`      | `/users/42` | Возвращает пользователя с id=42.             |
| Создать пользователя            | `POST`     | `/users`    | Создаёт нового пользователя (данные в теле). |
| Полностью обновить пользователя | `PUT`      | `/users/42` | Заменяет пользователя с id=42.               |
| Частично обновить               | `PATCH`    | `/users/42` | Изменяет отдельные поля.                     |
| Удалить пользователя            | `DELETE`   | `/users/42` | Удаляет пользователя.                        |

REST тесно связан с HTTP: методы HTTP (GET, POST, PUT, DELETE) используются как «глаголы» для операций над ресурсами, а коды ответов (200, 201, 404, 500) — для сообщения результата.

При проектировании REST API важно помнить про идемпотентность методов. Идемпотентным называется метод, повторный вызов которого даёт тот же результат на сервере, что и первый. К идемпотентным относятся `GET`, `PUT`, `DELETE`, `HEAD`, `OPTIONS`. Методы `POST` и `PATCH` — неидемпотентны (повторный POST создаст вторую запись, повторный PATCH может применить изменение дважды). 

>Подробнее про принципы проектирования можно почитать в [REST API Tutorial](https://restfulapi.net/), а про сравнение подходов — в документации [Microsoft: REST vs RPC](https://learn.microsoft.com/en-us/azure/architecture/microservices/design/api-design#rest-vs-rpc).

## 1. Протокол HTTP

HTTP (HyperText Transfer Protocol) — это протокол прикладного уровня, лежащий в основе передачи данных в вебе. Он работает по схеме «запрос-ответ» и не сохраняет состояние между запросами, что делает его масштабируемым, но требующим дополнительных механизмов (например, cookies) для организации сессий.

### Структура запросов и ответов

Сообщения HTTP как в запросе, так и в ответе имеют схожую структуру, состоящую из трёх частей, разделённых пустой строкой:

1.  **Стартовая строка** — описывает тип сообщения.
2.  **Заголовки** (Headers) — метаинформация о сообщении.
3.  **Тело** (Body, необязательно) — полезная нагрузка (данные).

**Стартовая строка запроса** содержит три элемента, разделённые пробелами:
*   **Метод** (например, `GET`, `POST`).
*   **URI** запрашиваемого ресурса (например, `/index.html`).
*   **Версия** протокола (например, `HTTP/1.1`).

```http
GET /index.html HTTP/1.1
```

**Стартовая строка ответа** (статусная строка) также содержит три элемента:
*   **Версия** протокола.
*   **Код состояния** (например, `200`, `404`).
*   **Пояснительная фраза** (например, `OK`, `Not Found`).

```http
HTTP/1.1 200 OK
```

За стартовой строкой следуют **заголовки**. Каждый заголовок — это пара `Имя: Значение`. Список заголовков завершается **пустой строкой**. Всё, что идёт после неё, — это **тело сообщения**. Тело может отсутствовать (например, в большинстве GET-запросов или в ответах с кодом `204 No Content`).

Пример полного HTTP-ответа:

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 1024

<!DOCTYPE html>
<html>...</html>
```

### Методы HTTP и идемпотентность

Метод HTTP указывает, какое действие клиент хочет выполнить над ресурсом. Помимо семантики, методы обладают двумя важными свойствами: **безопасность** (safe) и **идемпотентность** (idempotent).

*   **Безопасный метод** не изменяет состояние сервера. Он предназначен только для чтения.
*   **Идемпотентный метод** при повторном выполнении с теми же данными даёт тот же результат на сервере, что и при первом вызове. Это свойство критически важно для надёжности: если клиент не получил ответ (например, из-за обрыва связи), он может безопасно повторить идемпотентный запрос.

Вот основные методы и их свойства:

| Метод       | Назначение                                                          | Безопасный? | Идемпотентный? |
| :---------- | :------------------------------------------------------------------ | :---------- | :------------- |
| **GET**     | Запрос содержимого ресурса.                                         | Да          | Да             |
| **HEAD**    | Аналогичен GET, но ответ не содержит тела (только заголовки).       | Да          | Да             |
| **POST**    | Передача данных ресурсу (например, создание новой сущности).        | Нет         | **Нет**        |
| **PUT**     | Полная замена ресурса.                                              | Нет         | Да             |
| **PATCH**   | Частичное изменение ресурса.                                        | Нет         | **Нет**        |
| **DELETE**  | Удаление ресурса.                                                   | Нет         | Да             |
| **OPTIONS** | Определение возможностей сервера для ресурса (используется в CORS). | Да          | Да             |

Ключевой момент для запоминания: `POST` и `PATCH` — **неидемпотентны**. Дважды отправив POST-запрос на создание заказа, вы, скорее всего, создадите два заказа. Поэтому повторять такие запросы автоматически при ошибках нельзя.

### Коды состояния (Status Codes)

Код состояния — это трёхзначное число в ответе сервера, которое сообщает результат обработки запроса. Первая цифра кода определяет его класс:

*   **1xx (Informational)** — Информационные. Запрос получен, обработка продолжается. Редко встречаются в повседневной разработке (пример: `101 Switching Protocols` при переходе на WebSocket).
*   **2xx (Success)** — Успех. Запрос был успешно принят и обработан.
    *   `200 OK` — стандартный ответ на успешный запрос.
    *   `201 Created` — ресурс успешно создан (часто после `POST` или `PUT`).
    *   `204 No Content` — успех, но тело ответа отсутствует (например, после `DELETE`).
*   **3xx (Redirection)** — Перенаправление. Для выполнения запроса клиенту нужно перейти по другому URI.
    *   `301 Moved Permanently` — ресурс навсегда перемещён на новый адрес.
    *   `302 Found` — ресурс временно доступен по другому адресу.
    *   `304 Not Modified` — ресурс не изменился с момента последнего запроса (используется для кеширования).
*   **4xx (Client Error)** — Ошибка клиента. Запрос содержит синтаксическую ошибку или не может быть выполнен.
    *   `400 Bad Request` — сервер не понимает запрос из-за неверного синтаксиса.
    *   `401 Unauthorized` — для доступа к ресурсу требуется аутентификация.
    *   `403 Forbidden` — аутентификация пройдена, но у клиента нет прав на доступ к ресурсу.
    *   `404 Not Found` — ресурс не найден.
*   **5xx (Server Error)** — Ошибка сервера. Сервер не смог выполнить корректный запрос из-за внутренней ошибки.
    *   `500 Internal Server Error` — общая ошибка сервера.
    *   `502 Bad Gateway` — прокси-сервер получил неверный ответ от вышестоящего сервера.
    *   `503 Service Unavailable` — сервер временно перегружен или недоступен.

### Заголовки HTTP (Headers)

Заголовки передают метаинформацию о запросе или ответе. Они делятся на несколько групп, но для начала достаточно знать ключевые из них.

**Заголовки запроса:**
*   **`Host`**: Доменное имя сервера, к которому обращается клиент. Обязателен в HTTP/1.1, так как позволяет размещать несколько сайтов на одном IP-адресе.
*   **`User-Agent`**: Информация о клиенте (браузере, ОС).
*   **`Accept`**: Типы медиа (MIME-типы), которые клиент может принять в ответе (например, `text/html`, `application/json`).
*   **`Content-Type`**: Тип данных в теле запроса (например, `application/json` при отправке JSON).
*   **`Content-Length`**: Размер тела запроса в байтах.
*   **`Cookie`**: Отправляет ранее полученные от сервера cookies.

**Заголовки ответа:**
*   **`Content-Type`**: Тип данных в теле ответа. Критически важен для правильной интерпретации браузером.
*   **`Content-Length`**: Размер тела ответа в байтах.
*   **`Location`**: Используется в ответах `3xx` для указания нового URL при перенаправлении.
*   **`Set-Cookie`**: Устанавливает cookie на клиенте. Сервер отправляет этот заголовок, чтобы браузер сохранил пару «имя=значение» и отправлял её обратно в последующих запросах.

### Cookies и сессии

Мы уже знаем, что HTTP — **stateless-протокол**. Как же тогда работают корзины в интернет-магазинах или системы входа в аккаунт? Ответ — **cookies** и **сессии**.

**Cookie** — это небольшой фрагмент данных, который сервер отправляет браузеру через заголовок `Set-Cookie`. Браузер сохраняет его и автоматически прикрепляет к каждому последующему запросу к этому же серверу в заголовке `Cookie`.

**Сессия** — это механизм, который использует cookies для поддержания состояния. Сервер, получив запрос, создаёт уникальный идентификатор сессии (Session ID). Затем он отправляет его клиенту в cookie. При следующих запросах клиент автоматически отправляет этот Session ID, и сервер по нему «узнаёт» пользователя и восстанавливает связанные с ним данные (например, что лежит в корзине), которые хранятся на самом сервере.

### CORS

Современные веб-приложения часто состоят из клиента и сервера, расположенных на **разных доменах**. По умолчанию браузеры применяют политику **Same-Origin Policy (SOP)**, которая запрещает скриптам с одного сайта читать данные с другого.

**CORS (Cross-Origin Resource Sharing)** — это механизм, который позволяет серверу ослабить эту политику и разрешить кросс-доменные запросы. Для этого сервер добавляет в ответ специальные заголовки, главный из которых — `Access-Control-Allow-Origin`, где указывается домен, которому разрешён доступ (или `*` для всех).

Для «сложных» запросов (например, с методами `PUT`, `DELETE` или с нестандартными заголовками) браузер сначала отправляет **предварительный запрос (preflight)** методом `OPTIONS`. Он спрашивает у сервера разрешение на выполнение основного запроса. И только получив положительный ответ на preflight, браузер отправляет реальный запрос.

Если вы хотите углубиться в детали, рекомендую официальные спецификации: [RFC 9110: HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html) для методов, кодов и заголовков, [RFC 6265: HTTP State Management Mechanism](https://www.rfc-editor.org/rfc/rfc6265.html) для cookies, и документацию [MDN: CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/CORS) для кросс-доменных запросов.

## 2. Язык разметки HTML

HTML (HyperText Markup Language) — это стандартный язык разметки документов в интернете. Важно понимать, что это не язык программирования (он не является Тьюринг-полным, в нём нет переменных, циклов или условий), а язык описания структуры и содержимого веб-страницы, который интерпретируется браузером.

### Основы HTML и структура документа

Исторически HTML произошёл от **SGML** (Standard Generalized Markup Language) — мощного метаязыка разметки, который использовался для описания структуры документов. Существует также **XHTML** — более строгая версия HTML, основанная на XML. В XHTML требуется закрывать все теги, соблюдать регистр и правильно вкладывать элементы, иначе браузер выдаст ошибку. Обычный HTML (особенно начиная с HTML5) гораздо более «прощающий»: он прощает незакрытые теги и неточности. В HTML5 от строгого следования правилам SGML отказались, но сохранили обратную совместимость с предыдущими версиями (HTML4).

Любой HTML-документ должен начинаться с объявления версии — **`<!DOCTYPE html>`**. В старых версиях (HTML4, XHTML) этот тег выглядел как длинная строка со ссылкой на DTD (Document Type Definition) — файл с правилами грамматики. В HTML5 его сократили до одного короткого тега.

Часто спрашивают: можно ли вообще не указывать `<!DOCTYPE html>`? Технически — да, браузер отрисует страницу. Но если его нет, браузер переключится в так называемый **quirks mode** (режим совместимости со старыми браузерами). В этом режиме CSS-модель блока работает иначе (например, `box-sizing` по умолчанию ведёт себя как `content-box` со старыми багами, отступы считаются по-другому). Проверить текущий режим можно в консоли JavaScript через свойство `document.compatMode`. Если оно возвращает `"BackCompat"` — это quirks mode, а если `"CSS1Compat"` — стандартный режим. Поэтому `<!DOCTYPE html>` всегда нужно писать первой строкой.

Пример XHTML
```xhtml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE html PUBLIC "-//W3C//DTD XHTML 1.0 Strict//EN" "http://www.w3.org/TR/xhtml1/DTD/xhtml1-strict.dtd">
<html xmlns="http://www.w3.org/1999/xhtml" xml:lang="ru">
<head>
    <title>Пример XHTML</title>
</head>
<body>
    <p>Здесь все теги закрыты.<br /></p>
    <img src="image.png" alt="Картинка" />
</body>
</html>
```

Пример XML
```xml
<?xml version="1.0" encoding="UTF-8"?>
<library>
    <book id="1">
        <title>Веб-программирование</title>
        <author>Иванов И.И.</author>
        <year>2026</year>
    </book>
    <book id="2">
        <title>Ассемблер для начинающих</title>
        <author>Петров П.П.</author>
        <year>2025</year>
    </book>
</library>
```


### Теги, элементы и атрибуты

В обиходе мы часто путаем понятия «тег» и «элемент», но в контексте DOM (Document Object Model) это разные вещи. **Тег** — это синтаксис в исходном коде HTML (например, `<p>` или `</p>`). **Элемент** — это уже объект в памяти браузера, который включает в себя открывающий тег, закрывающий тег, всё содержимое между ними и его атрибуты. То есть `<p>Привет</p>` — это один элемент, состоящий из двух тегов.

**Атрибуты** задают дополнительную информацию об элементе. Они делятся на глобальные (доступные почти для всех тегов, например, `id`, `class`, `style`, `title`, `data-*`) и специфичные для конкретного тега (например, `href` для ссылок `<a>` или `src` для картинок `<img>`).

Отдельно стоит выделить **пустые теги (void elements)**. Это элементы, которые не могут иметь содержимого и поэтому не требуют закрывающего тега. В HTML5 таких тегов ровно 14: `<area>`, `<base>`, `<br>`, `<col>`, `<embed>`, `<hr>`, `<img>`, `<input>`, `<link>`, `<meta>`, `<param>`, `<source>`, `<track>`, `<wbr>`. Например, `<br>` просто переносит строку, а `<img>` вставляет картинку. При этом такие теги, как `<script>`, `<style>`, `<div>` или `<a>`, **не являются пустыми** — им обязательно нужен закрывающий тег (иначе браузер может «съесть» весь последующий код).

Примеры пустых (void) тегов
```html
<p>Первая строка<br>Вторая строка</p>
<hr>
<img src="cat.jpg" alt="Кот" width="200">
<input type="text" placeholder="Введите имя">
```

### Семантические теги и HTML5

Теоретически всю страницу можно сверстать одними `<div>` и `<span>`, но это считается плохой практикой. В HTML5 появились **семантические теги**: `<header>`, `<nav>`, `<main>`, `<article>`, `<section>`, `<aside>`, `<footer>`. Они не несут новой функциональности для браузера (с точки зрения отрисовки), но дают огромные преимущества:
1.  **Accessibility (Доступность)**: Скринридеры (программы для слепых) используют эти теги, чтобы пользователь мог быстро перемещаться по странице (например, перейти сразу к `<main>` или навигации `<nav>`).
2.  **SEO**: Поисковые роботы (Google, Яндекс) лучше понимают структуру страницы и её значимость.
3.  **Читаемость кода**: Разработчику гораздо проще ориентироваться в `<nav>`, чем в `<div class="navigation">`.

Помимо семантики, HTML5 принёс поддержку `<audio>` и `<video>` (без сторонних плагинов вроде Flash), новые типы полей ввода (date, time, email, range) и новые API для работы с графикой (`<canvas>`).

Пример базового HTML5 с семантическими тегами
```html
<!DOCTYPE html>
<html lang="ru">
<head>
    <meta charset="UTF-8">
    <meta name="viewport" content="width=device-width, initial-scale=1.0">
    <title>Семантический HTML5</title>
</head>
<body>
    <header>
        <h1>Мой блог</h1>
        <nav>
            <ul>
                <li><a href="#home">Главная</a></li>
                <li><a href="#about">Обо мне</a></li>
            </ul>
        </nav>
    </header>

    <main>
        <article>
            <h2>Как работают прототипы в JS</h2>
            <p>Опубликовано: <time datetime="2026-10-21">21 октября 2026</time></p>
            <section>
                <h3>Введение</h3>
                <p>В этой статье мы разберем...</p>
            </section>
        </article>
        
        <aside>
            <h3>Ссылки</h3>
            <p>Полезные ресурсы</p>
        </aside>
    </main>

    <footer>
        <p>&copy; 2026 Все права защищены.</p>
    </footer>
</body>
</html>
```

### HTML-формы

Формы предназначены для обмена данными между пользователем и сервером. Границы формы задаются тегом `<form>`, у которого есть два ключевых атрибута: `action` (URL, куда отправлять данные) и `method` (HTTP-метод: `GET` или `POST`).

Если не указывать метод, по умолчанию используется **GET**. В чём разница? 
*   **GET** передаёт данные в URL (в строке запроса, например `?name=John&age=25`). Это удобно для поиска или фильтрации, такую ссылку можно сохранить в закладки. Но у длины URL есть ограничения (около 2-8 КБ), а данные видны всем.
*   **POST** передаёт данные в теле HTTP-запроса. Нет ограничений на размер (можно передавать файлы), данные не видны в адресной строке. Используется для авторизации, создания заказов, загрузки файлов.
Важно помнить, что POST не делает данные «безопасными» просто потому, что они не видны в URL (они видны в DevTools и логах). Для безопасности всегда нужен HTTPS.

Для ввода данных используются различные теги: `<input>` (с типами `text`, `password`, `radio`, `checkbox`, `submit` и другими), `<textarea>` (многострочный текст), `<select>` (выпадающий список). В HTML5 появилась возможность валидировать данные прямо на клиенте без JavaScript: атрибуты `required` (обязательное поле), `pattern` (регулярное выражение), `min`/`max` (для чисел) и `type="email"`.

В одном документе может быть сколько угодно форм, но одновременно на сервер отправляется только одна. Кроме того, **вкладывать одну форму в другую запрещено** (это сломает отправку данных).

Пример HTML-формы (Метод GET)
```html
<!-- При отправке URL станет: /search?query=javascript&category=it -->
<form action="/search" method="GET">
    <label for="search-input">Поиск:</label>
    <input type="text" id="search-input" name="query" placeholder="Что ищем?">
    
    <label for="cat">Категория:</label>
    <select id="cat" name="category">
        <option value="all">Все</option>
        <option value="it">IT</option>
        <option value="design">Дизайн</option>
    </select>
    
    <button type="submit">Найти</button>
</form>
```

### HTML-сущности и XSS

В HTML некоторые символы имеют специальное значение, например, `<`, `>`, `&`. Если вы хотите вывести их на экран как текст, а не как часть разметки, нужно использовать **HTML-сущности**. Самая частая — `&lt;` для `<` и `&gt;` для `>`. Неразрывный пробел обозначается как `&nbsp;`, а амперсанд — `&amp;`.

Зачем это нужно? Это первый рубеж защиты от **XSS-атак (Cross-Site Scripting)**. XSS — это уязвимость, при которой злоумышленник внедряет вредоносный JavaScript-код на страницу, который затем выполняется в браузере других пользователей (например, крадёт куки или пароли). Если вы выводите пользовательский комментарий на страницу через `innerHTML` без экранирования сущностей, и пользователь написал `<script>alert('Взлом')</script>`, скрипт выполнится. Поэтому при работе с DOM в JavaScript безопаснее использовать `textContent` (который вставляет всё как текст), а не `innerHTML` (который парсит строку как HTML-код).

Пример HTML-сущностей
```html
<p>Чтобы выделить текст жирным, используйте тег &lt;b&gt;текст&lt;/b&gt;.</p>
<p>Символ амперсанда выглядит так: &amp; (это &amp;amp; в коде).</p>
<p>Неразрывный пробел: 100&nbsp;руб.</p>
<p>Копирайт: &copy; 2026. Стрелка вправо: &#8594;</p>
```

### Объектная модель документа (DOM)

**DOM (Document Object Model)** — это платформенно-независимый интерфейс, который представляет HTML-документ в виде дерева узлов (Nodes). Каждый тег, текст, комментарий — это узел этого дерева, связанный с другими отношениями «родитель-потомок». Именно через DOM JavaScript может динамически изменять страницу.

Для поиска элементов в дереве используются методы:
*   `document.getElementById('id')` — самый быстрый способ найти элемент по уникальному `id`.
*   `document.querySelector('css-селектор')` — находит **первый** элемент, подходящий под CSS-правило (например, `.form input[type="text"]`).
*   `document.querySelectorAll('css-селектор')` — возвращает **все** найденные элементы (в виде статичной коллекции NodeList).

Для изменения страницы можно использовать:
*   `element.textContent` — безопасно меняет только текст внутри элемента.
*   `element.innerHTML` — позволяет вставить HTML-код (опасно для пользовательских данных).
*   `document.createElement('div')` — создаёт новый узел в памяти.
*   `parent.appendChild(child)` — добавляет созданный узел в конец родителя.
*   `element.remove()` — удаляет элемент из дерева.

Если хотите проверить свой HTML-код на валидность (соответствие стандартам W3C) или узнать больше о спецификациях, используйте официальный [W3C Markup Validation Service](https://validator.w3.org/) и документацию [MDN Web Docs: HTML](https://developer.mozilla.org/en-US/docs/Web/HTML).

## 3. Каскадные таблицы стилей (CSS)

CSS (Cascading Style Sheets) — это язык описания внешнего вида документа. Его основная задача — отделить содержимое (HTML) от представления. Благодаря CSS один и тот же HTML-документ можно по-разному отобразить на экране, при печати или для людей с ограниченными возможностями (например, для скринридеров).

### Структура CSS и способы подключения

Таблица стилей состоит из набора правил. Каждое правило включает в себя **селектор** (указывает, к каким элементам применяется стиль) и **блок объявлений** (свойства и их значения), заключенный в фигурные скобки.

```css
селектор {
    свойство: значение;
    свойство: значение;
}
```

В CSS есть три способа подключения стилей к HTML-документу:

1.  **Inline-стили (Встроенные в тег)**: Задаются через атрибут `style` непосредственно в HTML-теге. Имеют самый высокий приоритет, но считаются плохой практикой, так как смешивают разметку и представление, усложняют поддержку и не кешируются браузером.
    ```html
    <p style="color: red; font-size: 16px;">Красный текст</p>
    ```
2.  **Встроенные стили (Internal)**: Блок `<style>` внутри `<head>`. Удобно для одностраничных проектов или быстрых прототипов.
    ```html
    <head>
        <style>
            p { color: blue; }
        </style>
    </head>
    ```
3.  **Внешние таблицы стилей (External)**: Самый правильный и распространенный способ. CSS выносится в отдельный файл `.css`, который подключается через тег `<link>`.
    ```html
    <head>
        <link rel="stylesheet" href="style.css">
    </head>
    ```

В реальных проектах, когда стилей становится много, разработчики задаются вопросом: как хранить цвета, шрифты и отступы так, чтобы их было легко менять. Здесь на сцену выходят препроцессоры и CSS-переменные, которые мы обсудим в конце этой главы.

### Селекторы и псевдоклассы

Селекторы — это способ «найти» нужные элементы в DOM-дереве. Они делятся на несколько категорий.

**Базовые селекторы:**
*   `*` — универсальный (выбирает все элементы).
*   `div` — по имени тега.
*   `.my-class` — по классу.
*   `#my-id` — по уникальному идентификатору.
*   `input[type="text"]` — по атрибуту.

**Комбинаторы (связи):**
*   `div p` — потомок (все `<p>` внутри `<div>` на любой глубине).
*   `div > p` — дочерний (только прямые потомки).
*   `h1 + p` — смежный (первый `<p>`, идущий сразу после `<h1>`).
*   `h1 ~ p` — родственный (все `<p>`, идущие после `<h1>` на том же уровне).

**Псевдоклассы** описывают состояние элемента или его положение в дереве. Их синтаксис — одинарное двоеточие:
*   `:hover` — наведение курсора.
*   `:focus` — фокус (например, в поле ввода).
*   `:nth-child(odd)` — выбор нечетных элементов.
*   `:checked` — выбранный чекбокс или радиокнопка.

**Псевдоэлементы** позволяют стилизовать часть элемента или создать виртуальный элемент, которого нет в HTML. Синтаксис — двойное двоеточие:
*   `::before` и `::after` — вставить контент до или после элемента (через свойство `content`).
*   `::first-letter` — первая буква текста.
*   `::placeholder` — текст-заглушка в поле ввода.

```css
/* Пример использования разных селекторов */
.form-table > tbody > tr > td:first-child {
    font-weight: bold;
}

input:focus {
    border-color: #4a90e2;
    outline: none;
}

a:hover::after {
    content: " ↗";
    font-size: 12px;
}
```

### Специфичность (Приоритеты) и каскад

Каскад — это механизм разрешения конфликтов. Если к одному элементу применяется несколько разных правил, браузер должен решить, какое из них победит. Для этого используется **специфичность** (вес) селекторов.

Специфичность не считается простой арифметикой в десятичной системе (как иногда ошибочно думают). Она представляет собой **кортеж из четырех чисел** (a, b, c, d), который сравнивается слева направо:
*   **a** — inline-стили (атрибут `style`).
*   **b** — идентификаторы (`#id`).
*   **c** — классы, псевдоклассы, атрибуты (`.class`, `:hover`, `[type="text"]`).
*   **d** — теги и псевдоэлементы (`div`, `::before`).

Правило с более высоким `a` побеждает. Если `a` равны, сравниваются `b` и так далее. Именно поэтому **один селектор по `id` (0, 1, 0, 0) всегда перебьет 11 классов (0, 0, 11, 0)**, и никакой порядок в файле это не изменит.

Исключением из всех правил является директива **`!important`**. Если она добавлена к свойству, оно перебивает любые другие стили (кроме другого `!important`).

Если часто возникает ситуация, когда стили «не применяются», приходится перебивать их через `!important`, это верный признак того, что архитектура CSS выстроена неправильно. Использование `!important` считается плохой практикой, потому что оно ломает естественный каскад и делает отладку настоящим кошмаром (вам придется добавлять новый `!important`, чтобы перебить старый).

Если специфичность двух правил одинакова, побеждает то правило, которое объявлено в файле **ниже**. Это и есть основа «каскада» (стили стекают сверху вниз).

### Шрифты и типографика

Для работы с текстом используется ряд свойств: `font-family`, `font-size`, `font-weight` (жирность), `line-height` (межстрочный интервал), `letter-spacing` (расстояние между буквами) и `text-align`.

**Единицы измерения размера:**
*   `px` (пиксели) — абсолютная единица, не зависит от настроек пользователя.
*   `%` — относительно размера родительского элемента.
*   `em` — относительно размера шрифта родителя. Коварная единица: если у родителя 16px, а у ребенка `font-size: 1.2em`, то размер будет 19.2px. При глубокой вложенности шрифты могут разрастись до гигантских размеров.
*   `rem` (root em) — относительно размера шрифта корневого элемента (`<html>`). Самый безопасный и предсказуемый вариант для адаптивной верстки.
*   `vw` / `vh` — относительно ширины или высоты окна браузера.

**Font stack (стек шрифтов)** — это список шрифтов через запятую в свойстве `font-family`. Браузер берет первый шрифт из списка, который установлен в системе пользователя. В конце списка всегда указывается обобщенное семейство (`serif`, `sans-serif`, `monospace`), чтобы браузер знал, какой тип шрифта использовать в крайнем случае.

```css
body {
    /* Если нет Segoe UI (Windows), возьмется Helvetica (macOS), иначе любой sans-serif */
    font-family: 'Segoe UI', 'Helvetica Neue', Arial, sans-serif;
    font-size: 1rem; /* Обычно 16px, если в html не задано иное */
    line-height: 1.5; /* Множитель, масштабируется вместе с размером шрифта */
}
```

**Подключение кастомных шрифтов (`@font-face`).**
Если дизайнер хочет использовать фирменный шрифт, его нужно загрузить с сервера. Для этого используется директива `@font-face`. Современный стандарт — формат **WOFF2** (лучшее сжатие и поддержка всеми браузерами).

```css
@font-face {
    font-family: 'MyCustomFont';
    src: url('fonts/MyCustomFont.woff2') format('woff2'),
         url('fonts/MyCustomFont.woff') format('woff');
    font-weight: 400;
    font-style: normal;
    /* swap — показывать системный шрифт, пока кастомный грузится */
    font-display: swap; 
}
```

Посмотреть все возможные @-правила (или at-rules) можно посмотреть по  [этой ссылке](https://developer.mozilla.org/en-US/docs/Web/CSS/At-rule).

### Препроцессоры (Sass/SCSS, Less)

В обычном CSS нельзя объявить переменную, использовать цикл или написать функцию. В больших проектах это превращается в проблему. На помощь приходят **препроцессоры** — надстройки над CSS, которые компилируются в обычный CSS перед тем, как попасть в браузер.

**Основные возможности препроцессоров:**
1.  **Переменные** (позволяют задать цвет или размер в одном месте).
2.  **Вложенность** (вложенные селекторы пишутся внутри родительских).
3.  **Миксины (mixins)** (переиспользуемые блоки стилей, похожие на функции).
4.  **Математические операции** (можно делить, умножать, складывать значения).
5.  **Циклы и условия** (генерация множества классов, например, для сетки).

Браузеры **не понимают** код препроцессоров. Для них используются специальные программы-компиляторы (например, в сборщиках Webpack, Vite или через CLI).

На лекции часто задают вопрос: *являются ли препроцессоры языками программирования?* Здесь интересный нюанс: **Sass** является Тьюринг-полным языком (в 2014 году на нём даже реализовали клеточный автомат Rule 110), а вот **Less** — нет, он гораздо проще и ближе к обычному CSS.

**В чём разница между Less, Sass и SCSS?**
*   **Less**: CSS-подобный синтаксис, использует `@var`. Изначально компилировался в браузере через JS, но сейчас чаще на сервере.
*   **Sass (синтаксис Indented)**: Использует отступы вместо фигурных скобок и точек с запятой. Выглядит лаконично, но непривычно.
*   **SCSS (Sassy CSS)**: Самый популярный диалект. Это тот же Sass, но с привычным для CSS синтаксисом (с фигурными скобками). Любой валидный CSS — это валидный SCSS.

*Пример кода на SCSS:*
```scss
// Переменные
$primary-color: #4a90e2;
$padding-base: 10px;

// Миксин для кнопки
@mixin button-styles {
    padding: $padding-base;
    border: none;
    border-radius: 4px;
}

// Вложенность
.nav {
    background: white;
    @include button-styles;
    
    // Вложенный селектор (эквивалентно .nav a)
    a {
        color: $primary-color;
        
        // Псевдокласс (эквивалентно .nav a:hover)
        &:hover {
            text-decoration: underline;
        }
    }
}
```

*Во что это скомпилируется (обычный CSS):*
```css
.nav {
    background: white;
    padding: 10px;
    border: none;
    border-radius: 4px;
}
.nav a {
    color: #4a90e2;
}
.nav a:hover {
    text-decoration: underline;
}
```
Если вы хотите подробнее изучить синтаксис и возможности SCSS, рекомендую официальную документацию [Sass Documentation](https://sass-lang.com/documentation/), а для работы с CSS-переменными и современными свойствами — справочник [MDN: CSS](https://developer.mozilla.org/en-US/docs/Web/CSS).

## 4. Клиентский JavaScript (База)

JavaScript — это объектно-ориентированный скриптовый язык программирования, который используется для придания интерактивности веб-страницам. Изначально он создавался для работы на клиенте (в браузере), но сегодня с помощью среды Node.js его используют и на сервере. Структурно язык делится на три части: ядро (ECMAScript), объектную модель документа (DOM) и объектную модель браузера (BOM).

### Особенности языка

JavaScript обладает рядом архитектурных черт, которые отличают его от C++, Java или Python.

1.  **Динамическая и слабая типизация.** Вам не нужно указывать тип переменной при объявлении. Более того, одна и та же переменная может хранить число, строку, а затем объект. Слабая типизация означает, что JS автоматически приводит типы при операциях. Например, выражение `"5" + 3` вернёт строку `"53"`, а `"5" - 3` вернёт число `2`. Именно из-за этого неожиданного поведения в JS всегда рекомендуют использовать оператор строгого равенства `===` вместо нестрогого `==`.
2.  **Функции как объекты первого класса.** В JavaScript функция — это не просто блок кода, а полноценный объект. Её можно присвоить переменной, передать в другую функцию как аргумент или вернуть из функции как результат.
3.  **Автоматическое управление памятью.** Вам не нужно вручную выделять и очищать память (как в C или C++). Сборщик мусора (Garbage Collector) сам находит объекты, на которые больше нет ссылок, и удаляет их.
4.  **Прототипное программирование.** Вместо классического наследования (как в Java), в основе JS лежит механизм прототипов.

### Области видимости и замыкания

До 2015 года в JS переменные объявлялись только через ключевое слово `var`. У него есть две главные проблемы: он имеет **функциональную область видимости** (игнорирует блоки `{}`, например, внутри `if` или `for`) и подвержен **поднятию (hoisting)**. Это значит, что переменная `var` как бы «поднимается» в начало своей функции, и при обращении к ней до объявления она вернёт `undefined`, а не вызовет ошибку.

С появлением стандарта ES6 (ES2015) добавили `let` и `const`. Они имеют **блочную область видимости** (видны только внутри ближайших `{}`) и находятся во **временной мёртвой зоне (Temporal Dead Zone)**. Это означает, что если вы попытаетесь обратиться к `let` или `const` до их фактического объявления в коде, вы получите ошибку `ReferenceError`. Разница между ними лишь в том, что `let` позволяет переопределять значение переменной, а `const` — запрещает (хотя свойства объекта, объявленного через `const`, менять можно).

Один из самых важных вопросов на собеседованиях: **что такое замыкание (closure)?** Замыкание — это механизм, при котором внутренняя функция «запоминает» переменные из своей внешней области видимости, даже после того, как внешняя функция завершила свою работу. Посмотрим на классический пример со счётчиком:

```javascript
function makeCounter() {
    let count = 0; // локальная переменная

    return function() {
        count++; 
        return count;
    };
}

const counter = makeCounter();
console.log(counter()); // 1
console.log(counter()); // 2
```
Функция `makeCounter()` отработала и завершилась, её переменные должны были быть уничтожены сборщиком мусора, но благодаря замыканию возвращённая анонимная функция продолжает «держать» переменную `count` в памяти и может её изменять. Замыкания широко используются для создания приватных переменных, счётчиков и каррирования функций.

### Контекст `this`

Ключевое слово `this` — головная боль многих новичков. В отличие от многих других языков, в JavaScript значение `this` определяется **в момент вызова функции**, а не в момент её объявления. Оно зависит от того, как именно была вызвана функция.

*   **Обычный вызов:** `function foo() { console.log(this); } foo();` — здесь `this` указывает на глобальный объект (`window` в браузере) или `undefined`, если включён строгий режим (`'use strict'`).
*   **Вызов как метод объекта:** Если функция вызывается как свойство объекта, `this` указывает на этот объект. 
    ```javascript
    const user = {
        name: "Иван",
        greet() { console.log(this.name); }
    };
    user.greet(); // "Иван" (this === user)
    ```
*   **Вызов через конструктор (`new`):** Когда функция вызывается с оператором `new`, создаётся новый пустой объект, и `this` начинает указывать на него.
*   **Явное указание контекста:** Методы `.call()`, `.apply()` и `.bind()` позволяют принудительно передать объект, который станет `this`.
*   **Стрелочные функции:** Появились в ES6 и **не имеют своего собственного `this`**. Они берут `this` из внешнего (лексического) окружения. Это очень удобно, когда вы передаёте функцию как колбэк (например, в `setTimeout`), иначе `this` бы терялось.

### Прототипное наследование и классы

JavaScript — это язык, основанный на прототипах. Если вы обращаетесь к свойству или методу объекта, которого у него нет, движок JS не выдаст сразу ошибку. Он пойдёт по так называемой **цепочке прототипов** (`__proto__` или `[[Prototype]]`) и будет искать это свойство у «родителя», затем у «родителя родителя» и так до тех пор, пока не дойдёт до `null`.

```javascript
const animal = {
    speak() { console.log("Издаёт звук"); }
};

const dog = Object.create(animal); // dog прототипно наследует animal
dog.speak(); // "Издаёт звук" — метод взят из прототипа animal
```

В ES6 появилось ключевое слово `class`. Это **синтаксический сахар** над прототипным наследованием. Под капотом всё работает точно так же, как с `Object.create` и функциями-конструкторами, просто выглядит знакомо для тех, кто писал на Java или C#. Классы поддерживают наследование через `extends` и вызов родительского конструктора через `super()`.

### Асинхронность и Event Loop

JavaScript — **однопоточный** язык. В один момент времени он может выполнять только одну инструкцию. Если бы все операции выполнялись синхронно, то любая загрузка данных из сети или тяжелое вычисление полностью бы «вешали» браузер: страница переставала бы реагировать на клики и прокрутку.

Чтобы этого избежать, используется механизм **Event Loop** (цикл событий). Он состоит из нескольких частей:
1.  **Call Stack (Стек вызовов)** — здесь выполняется ваш синхронный код.
2.  **Web API** — функции, которые браузер выполняет в фоне (таймеры `setTimeout`, запросы `fetch`, обработчики кликов). JS просто передает им задачу и идёт дальше.
3.  **Task Queue (Очередь макрозадач)** — сюда попадают колбэки по завершении операций Web API (например, сработал таймер).
4.  **Microtask Queue (Очередь микрозадач)** — сюда попадают колбэки промисов (`.then()`, `async/await`).

**Как это работает:** Когда стек вызовов пуст, Event Loop смотрит в очередь. Сначала он полностью очищает **очередь микрозадач** (промисы), и только потом берёт **одну** макрозадачу (таймер или событие) и закидывает её в стек.

Классический вопрос на собеседовании: в каком порядке выведутся числа?
```javascript
console.log('1');
setTimeout(() => console.log('2'), 0);
Promise.resolve().then(() => console.log('3'));
console.log('4');
```
Ответ: `1`, `4`, `3`, `2`. Сначала выполнится весь синхронный код (`1` и `4`). Таймер уйдёт в Web API, а колбэк промиса — в микрозадачи. После очистки стека Event Loop сначала выполнит микрозадачу (`3`), и только затем возьмёт из очереди макрозадачу (`2`).

Если хотите разобраться в JavaScript глубже, лучший ресурс — это онлайн-учебник [learn.javascript.ru](https://learn.javascript.ru/) (переведен на русский и очень подробный) и официальная документация [MDN Web Docs: JavaScript](https://developer.mozilla.org/en-US/docs/Web/JavaScript).

## 5. Современный JavaScript (ECMAScript 6+)

JavaScript — это живой язык, который развивается по стандарту **ECMAScript** (сокращённо ES). Начиная с 2015 года новые версии стандарта выходят каждый год. Версии обозначают либо по номеру (ES6, ES7), либо по году (ES2015, ES2016). До ES6 язык не обновлялся почти шесть лет, поэтому ES2015 стал самым масштабным обновлением в истории JavaScript. Дальнейшие версии добавляли возможности постепенно.

### Ключевые нововведения ES6 (ES2015)

ES6 принёс так много, что после него язык стал ощущаться другим. Основные изменения можно разделить на синтаксические улучшения и новые встроенные механизмы.

**Стрелочные функции** — это короткий синтаксис для объявления функций. Они не только экономят символы, но и решают проблему «потерянного `this`»: стрелочная функция не создаёт собственный контекст, а берёт его из окружающего кода. Именно поэтому стрелочные функции идеально подходят для колбэков в `setTimeout`, `map`, `filter` и обработчиках событий.

```javascript
// Обычная функция
const sum1 = function(a, b) { return a + b; };

// Стрелочная функция
const sum2 = (a, b) => a + b;

// Если тело — одно выражение, return пишется неявно.
// Если нужно вернуть объект, его оборачивают в круглые скобки:
const makeUser = (name) => ({ name });
```

Важно запомнить: стрелочные функции **нельзя использовать как конструкторы** (с `new`), у них нет своего `arguments` и своего `this`. Для методов объектов, которым нужен доступ к самому объекту через `this`, лучше подходят обычные функции.

**Шаблонные строки** (template literals) — это строки, заключённые в обратные кавычки. Они позволяют вставлять выражения через `${...}` и писать многострочный текст без символов переноса `\n`. Это делает код чище, особенно при генерации HTML или сообщений.

```javascript
const name = "Рома";
const age = 20;

const greeting = `Привет, ${name}! Через год тебе будет ${age + 1}.`;
```

**Деструктуризация** позволяет «разобрать» массив или объект на отдельные переменные за одно присваивание. Это особенно удобно при работе с ответами от API или параметрами функций.

```javascript
// Массив
const [first, second, ...rest] = [1, 2, 3, 4, 5];
// first = 1, second = 2, rest = [3, 4, 5]

// Объект
const user = { name: "Рома", age: 20 };
const { name, age } = user;

// В параметрах функции
function draw({ x, y, r }) {
    // ...
}
```

**Spread и rest** — это два применения одного и того же синтаксиса `...`. В **rest** (`...args`) оператор собирает оставшиеся аргументы или элементы в массив. В **spread** (`...arr`) он, наоборот, «разворачивает» массив или объект на отдельные значения.

```javascript
// Rest: собрать все аргументы после первого в массив
function log(format, ...params) {
    console.log(format, params);
}

// Spread: объединить массивы или объекты
const arr1 = [1, 2, 3];
const arr2 = [...arr1, 4, 5]; // [1, 2, 3, 4, 5]

const obj1 = { a: 1 };
const obj2 = { ...obj1, b: 2 }; // { a: 1, b: 2 }
```

**Промисы (Promises)** — это объект, который представляет результат асинхронной операции, который станет доступен в будущем. Промис может находиться в одном из трёх состояний: `pending` (ожидание), `fulfilled` (успех) или `rejected` (ошибка). Вместо вложенных колбэков (которые раньше приводили к «аду колбэков») теперь можно выстраивать цепочки `.then()` и обрабатывать ошибки через `.catch()`.

```javascript
fetch('/api/points')
    .then(response => response.json())
    .then(data => console.log(data))
    .catch(error => console.error('Ошибка:', error));
```

**Модули** — это механизм, позволяющий разбивать код на отдельные файлы и явно указывать, что из файла экспортируется и что импортируется. До ES6 приходилось использовать глобальные переменные или сторонние библиотеки. Теперь в браузере достаточно указать `<script type="module">`, а в Node.js — использовать расширение `.mjs` или настройку `"type": "module"` в `package.json`.

```javascript
// math.js
export const PI = 3.14;
export function add(a, b) { return a + b; }

// main.js
import { PI, add } from './math.js';
```

Помимо перечисленного, ES6 добавил `let` и `const` (блочная область видимости вместо `var`), синтаксис `class` (синтаксический сахар над прототипами), новые коллекции `Map` и `Set`, генераторы и цикл `for...of`. Подробный разбор каждого из этих механизмов есть в [учебнике learn.javascript.ru](https://learn.javascript.ru/es-modern) и в документации [MDN: JavaScript](https://developer.mozilla.org/ru/docs/Web/JavaScript).

### ES7 - ES2022: что добавили дальше

После ES6 стандарт перешёл на ежегодный цикл. Версии ES7 (ES2016) и ES8 (ES2017) были небольшими, но содержали важные практические улучшения. Начиная с ES2020 язык получил несколько возможностей, которые сильно упростили повседневную разработку.

**ES7 (ES2016)** добавил всего две вещи: метод `Array.prototype.includes()` для проверки наличия элемента в массиве (который, в отличие от `indexOf`, корректно работает с `NaN`) и оператор возведения в степень `**`.

```javascript
[1, 2, 3].includes(2); // true
2 ** 10; // 1024
```

**ES8 (ES2017)** принёс **`async/await`** — синтаксический сахар над промисами, который позволяет писать асинхронный код так, будто он синхронный. Функция, объявленная с `async`, всегда возвращает промис, а `await` приостанавливает выполнение до тех пор, пока промис не разрешится. Внутри `async`-функции можно использовать обычный `try/catch` для обработки ошибок.

```javascript
async function loadPoints() {
    try {
        const response = await fetch('/api/points');
        const data = await response.json();
        return data;
    } catch (error) {
        console.error('Ошибка загрузки:', error);
    }
}
```

В том же году появились `Object.entries()` и `Object.values()` для получения массивов пар «ключ-значение» и просто значений из объекта, а также методы `String.prototype.padStart()` и `padEnd()` для дополнения строки символами до нужной длины.

**ES2020** добавил две возможности, которые сегодня встречаются практически в каждом проекте. **Опциональная цепочка (`?.`)** позволяет безопасно обращаться к вложенным свойствам, не проверяя каждый уровень на `null` или `undefined`. Если на каком-то этапе цепочки встречается `null` или `undefined`, выражение целиком возвращает `undefined`, а не выбрасывает ошибку.

```javascript
const city = user?.address?.city;
// Если user или address равен null/undefined, city будет undefined.
```

**Нулевое слияние (`??`)** — это оператор, который возвращает правый операнд только в том случае, если левый равен `null` или `undefined`. Его часто путают с логическим ИЛИ (`||`), но разница принципиальна: `||` срабатывает на **любое** «ложное» значение, включая `0`, пустую строку и `false`. Если `0` или `""` являются для вас допустимыми значениями, используйте `??`, иначе логика сломается.

```javascript
const count = input ?? 10; // Если input === 0, вернётся 0, а не 10.
const count2 = input || 10; // Если input === 0, вернётся 10 — часто это ошибка.
```

**ES2022** завершил давнюю проблему инкапсуляции в классах, добавив **приватные поля и методы** с префиксом `#`. Такие поля доступны только внутри класса и недоступны снаружи, даже через квадратные скобки. Это настоящая инкапсуляция, а не соглашение об именовании вроде `_private`, которое раньше использовали разработчики.

```javascript
class User {
    #password;

    constructor(password) {
        this.#password = password;
    }

    checkPassword(input) {
        return input === this.#password;
    }
}

const user = new User('secret');
user.#password; // SyntaxError: приватное поле недоступно снаружи
```

В том же году появился **top-level await**, позволяющий использовать `await` на верхнем уровне модуля без обёртки в `async`-функцию. Это удобно, когда модулю нужно дождаться загрузки ресурса перед тем, как экспортировать значения. Также был добавлен метод `.at()` для массивов и строк, который поддерживает отрицательные индексы (`arr.at(-1)` возвращает последний элемент).

С полной хронологией версий и списком возможностей каждой из них можно ознакомиться в документации [MDN: ECMAScript](https://developer.mozilla.org/ru/docs/Web/JavaScript/JavaScript_technologies_overview) и в таблице совместимости [kangax.github.io/compat-table](https://kangax.github.io/compat-table/es6/).

## 6. Асинхронное клиент-серверное взаимодействие (AJAX)

В ранние годы веба любое взаимодействие с сервером требовало полной перезагрузки страницы. Если вы нажимали «Отправить» в форме, браузер отправлял данные и загружал новую HTML-страницу с нуля. Это было медленно, дергало интерфейс и расходовало много трафика. Решением этой проблемы стала концепция AJAX.

### DHTML и AJAX

**DHTML (Dynamic HTML)** — это не отдельный язык, а собирательное название подхода к созданию интерактивных страниц. Он объединяет в себе четыре технологии: статичный HTML, каскадные таблицы стилей (CSS), язык сценариев JavaScript и объектную модель документа (DOM). DHTML позволяет менять внешний вид и содержимое страницы на лету, после того как она уже загружена.

Следующим шагом стала технология **AJAX (Asynchronous JavaScript and XML)**. Вопреки названию, AJAX — это не язык и не библиотека. Это **архитектурный подход**, при котором JavaScript-код может обмениваться данными с сервером «в фоне», не блокируя и не перезагружая текущую страницу. Данные могут передаваться в формате XML, JSON, HTML или обычным текстом (JSON сегодня используется практически повсеместно).

Суть AJAX в том, что страница загружается один раз, а дальше все изменения (подгрузка комментариев, лайки, обновление ленты) происходят через фоновые запросы и точечное изменение DOM. Именно так работают современные соцсети и почтовые клиенты вроде Gmail. Если бы AJAX не существовало, каждое нажатие на «лайк» перезагружало бы всю страницу целиком.

Для реализации AJAX-запросов исторически использовался объект `XMLHttpRequest`, а сегодня — современный `Fetch API`.

### XMLHttpRequest и Fetch API

**XMLHttpRequest (XHR)** появился в браузере Internet Explorer ещё в 1999 году. Долгое время это был единственный способ делать фоновые запросы. Однако у него были серьёзные недостатки: сложный синтаксис, работа через колбэки (что приводило к «аду колбэков» при сложных цепочках запросов) и не очень удобная обработка ошибок.

Пример запроса через XHR выглядит громоздко:
```javascript
const xhr = new XMLHttpRequest();
xhr.open('GET', '/api/points', true);
xhr.onreadystatechange = function() {
    if (xhr.readyState === 4) {
        if (xhr.status === 200) {
            console.log(JSON.parse(xhr.responseText));
        } else {
            console.error('Ошибка:', xhr.status);
        }
    }
};
xhr.send();
```

С развитием стандартов в браузерах появился **Fetch API** — современная замена XHR. Fetch работает на промисах, что позволяет писать более чистый и понятный код, а также использовать синтаксис `async/await`.

```javascript
// Запрос через Fetch с использованием async/await
async function loadPoints() {
    try {
        const response = await fetch('/api/points');
        if (!response.ok) { // Fetch не выдает ошибку при 404, нужно проверять вручную
            throw new Error(`Ошибка HTTP: ${response.status}`);
        }
        const data = await response.json();
        console.log(data);
    } catch (error) {
        console.error('Сетевая ошибка или ошибка парсинга:', error);
    }
}
```

**Почему Fetch лучше?** Он лучше читается, легко комбинируется с современными возможностями языка (промисы, деструктуризация, `async/await`) и стал частью стандарта браузера (не нужно подключать внешние библиотеки). Стоит отметить одну известную особенность: в отличие от XHR, `fetch()` не отклоняет промис при статусах ответа 4xx или 5xx (например, при 404). Он считает запрос успешным, если сервер вообще смог ответить. Поэтому разработчики всегда проверяют свойство `response.ok` (которое истинно только для статусов 200-299).

Если хотите узнать, как работают запросы «под капотом» или как настраивать CORS, документация [MDN: Fetch API](https://developer.mozilla.org/ru/docs/Web/API/Fetch_API) и статья [MDN: AJAX](https://developer.mozilla.org/ru/docs/Web/Guide/AJAX) — лучший источник.

### Библиотека jQuery (исторический контекст)

Сегодня JavaScript развивается стремительно, но так было не всегда. В середине 2000-х годов главной болью веб-разработчиков была **кроссбраузерность**. Код, который работал в Firefox, мог сломаться в Internet Explorer, а в Safari вести себя совершенно иначе. Особенно это касалось работы с DOM и AJAX-запросами.

На этом фоне в 2006 году появилась библиотека **jQuery**. Её слоганом было *«Write less, do more»* (пиши меньше, делай больше). Она предложила единый, удобный API, который скрывал все различия между браузерами.

jQuery давала разработчикам три главные вещи:
1.  **Простой поиск элементов и манипуляция DOM**: Вместо `document.getElementById` или `document.querySelector` можно было писать `$('.my-class')` и применять к ним цепочки методов.
2.  **Унифицированный AJAX**: Запрос через `$.ajax()` работал одинаково во всех браузерах и не требовал написания десятков строк.
3.  **Анимации и эффекты**: Методы вроде `.fadeIn()`, `.slideUp()` позволяли делать красивые переходы без сложных CSS-хаков.

Пример работы с DOM в jQuery:
```javascript
// Найти все ссылки, добавить класс и обработать клик
$('a.external')
    .addClass('highlight')
    .on('click', function(event) {
        event.preventDefault();
        alert('Переход отменён');
    });
```

С появлением стандарта **ES6 (ES2015)** и современных браузерных API (Fetch, `querySelector`, `classList`, CSS-анимации), необходимость в jQuery практически отпала. Современные браузеры работают по единым стандартам, и сегодня писать на нативном JS зачастую проще, чем подключать ради этого целую библиотеку (весом в ~30 КБ).

Тем не менее, jQuery остаётся важной частью истории веба. В старых проектах (легаси-коде) она встречается до сих пор, а понимание её принципов (например, цепочек вызовов и работы с селекторами) полезно для чтения чужого кода и поддержки существующих сайтов.

## 7. Серверные сценарии (Классические интернет-приложения)

Когда-то веб состоял исключительно из статических HTML-страниц. Но бизнесу нужны были корзины товаров, базы пользователей и генерация контента на лету. Так появились **интернет-приложения** — сайты с динамической функциональностью на стороне сервера. Вместо того чтобы отдавать готовый файл с диска, сервер стал вызывать специальные программы-сценарии, которые генерировали HTML-код «на лету» в зависимости от запроса пользователя.

### CGI (Common Gateway Interface)

**CGI** — это самый первый и простейший стандарт взаимодействия веб-сервера с внешними программами. Идея проста: когда на сервер приходит HTTP-запрос, веб-сервер (например, Apache) запускает отдельный исполняемый файл (написанный на Perl, C, Python или любом другом языке). Данные от браузера передаются этой программе через переменные окружения и стандартный поток ввода (`stdin`), а результат работы программа пишет в стандартный поток вывода (`stdout`), который сервер затем отправляет клиенту.

Главное преимущество CGI — **независимость от языка**. Программа может быть написана хоть на Bash, главное, чтобы она умела читать `stdin` и писать в `stdout`. Кроме того, программы изолированы друг от друга: если один CGI-скрипт упадет с ошибкой, он не потянет за собой весь веб-сервер.

Однако у CGI есть фатальный недостаток для высоких нагрузок: **на каждый запрос создается новый процесс**. Операционная система тратит много ресурсов на создание процесса и выделение памяти. Если на сайт одновременно зайдут 1000 человек, сервер попытается запустить 1000 процессов, что быстро исчерпает оперативную память и загрузит процессор. Из-за этого CGI сегодня практически не используется для высоконагруженных систем. Здесь часто возникает вопрос: почему CGI-скрипты так медленно работают? Ответ кроется именно в накладных расходах на постоянное порождение новых процессов (fork/exec) операционной системой.

### FastCGI

**FastCGI** — это эволюция CGI, созданная для решения проблемы производительности. Вместо того чтобы запускать новый процесс на каждый запрос, FastCGI использует **пул долгоживущих процессов**. Один и тот же процесс может обработать тысячи запросов подряд.

Взаимодействие между веб-сервером и FastCGI-процессом происходит не через стандартные потоки ввода/вывода, а через сокеты (UNIX Domain Sockets или TCP/IP). Для общения по TCP/IP используется бинарный протокол, который позволяет эффективно передавать любые данные (HTTP-заголовки, тело запроса и ответа). 

Именно этот стандарт лежит в основе работы современных PHP (через `PHP-FPM`), Python (через `uWSGI` или `Gunicorn`) и других языков в связке с веб-серверами Nginx или Apache. Управление процессами (сколько их запускать, когда убивать лишние) берет на себя менеджер процессов, что делает архитектуру очень гибкой.

### Java Servlets (Сервлеты)

Java пошла своим путем. Вместо того чтобы запускать отдельные процессы (как CGI) или управлять ими через сокеты (как FastCGI), платформа **Java EE (Enterprise Edition)** предложила концепцию **сервлетов**. 

**Сервлет** — это Java-класс, который обрабатывает HTTP-запросы. Главное отличие от CGI в том, что сервлеты работают **внутри одного процесса** (виртуальной машины Java) и обрабатывают запросы в **отдельных потоках**, а не процессах. Потоки (threads) занимают гораздо меньше памяти и переключаются быстрее, чем процессы. Один экземпляр сервлета может одновременно обслуживать сотни и тысячи пользователей.

Сервлеты лишены проблемы «медленного запуска» CGI: они загружаются в память один раз при старте и живут там. К их плюсам можно отнести кроссплатформенность (благодаря JVM), высокую скорость и безопасность. Однако у них тоже есть недостаток: смешивание логики и представления. Писать HTML-код через `out.println("<html>...")` в Java-классе крайне неудобно и чревато ошибками. Это привело к созданию JSP (JavaServer Pages) и MVC-архитектуры, но это уже тема следующих лекций.

### Архитектура веб-контейнера и жизненный цикл сервлета

Сервлеты не запускаются сами по себе. Им нужна среда выполнения — **веб-контейнер** (или контейнер сервлетов). Самые популярные из них: **Apache Tomcat**, Jetty, JBoss. Веб-контейнер — это программа, которая принимает HTTP-запросы от клиента, преобразует их в Java-объекты и передает нужному сервлету.

Жизненным циклом сервлета полностью управляет контейнер. Разработчик не создает объекты сервлетов через `new`, это делает Tomcat. Процесс состоит из нескольких строгих этапов:

1.  **Загрузка класса:** Контейнер находит класс сервлета (обычно по конфигурации в `web.xml` или аннотации `@WebServlet`) и загружает его в память.
2.  **Создание экземпляра:** Контейнер вызывает конструктор по умолчанию. Создается ровно один экземпляр сервлета на всё время работы приложения.
3.  **Инициализация (`init()`):** Вызывается метод `init(ServletConfig)`. Здесь сервлет может прочитать настройки, подключиться к базе данных или загрузить конфигурацию.
4.  **Обработка запросов (`service()`):** Когда приходит запрос, контейнер выделяет для него отдельный поток и вызывает метод `service()`. Этот метод определяет тип HTTP-запроса (GET, POST) и вызывает соответствующий метод — `doGet()` или `doPost()`.
5.  **Уничтожение (`destroy()`):** Когда контейнер решает остановить приложение (например, при выключении сервера), он вызывает метод `destroy()`, где можно закрыть соединения с базой данных и освободить ресурсы.

Пример простейшего сервлета, который отвечает на GET-запрос:

```java
import javax.servlet.http.*;
import java.io.*;

public class HelloServlet extends HttpServlet {
    
    @Override
    public void init() {
        // Вызывается один раз при старте
        System.out.println("Сервлет инициализирован");
    }

    @Override
    protected void doGet(HttpServletRequest request, HttpServletResponse response) 
            throws IOException {
        // Вызывается на каждый GET-запрос
        response.setContentType("text/html;charset=UTF-8");
        PrintWriter out = response.getWriter();
        out.println("<html><body>");
        out.println("<h1>Привет из сервлета!</h1>");
        out.println("</body></html>");
    }

    @Override
    public void destroy() {
        // Вызывается при остановке контейнера
        System.out.println("Сервлет уничтожен");
    }
}
```
